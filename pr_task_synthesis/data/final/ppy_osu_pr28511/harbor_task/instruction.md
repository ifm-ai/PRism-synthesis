The editor currently lacks a robust way for users to jump to an arbitrary point in a beatmap by typing a timestamp into the bottom‑bar input field. Users need to be able to enter timestamps in a variety of common forms – full timestamps with minutes, seconds and milliseconds, abbreviated forms such as "mm:ss" or just a number of milliseconds, and optionally a selection clause in parentheses that references a specific hit‑object. When a valid timestamp is entered, the editor should move the playback cursor to the corresponding time. If a selection clause is present, the editor must also locate the hit‑object(s) matching that clause and highlight them, delegating the exact selection logic to the active ruleset.

If the entered string cannot be interpreted as a timestamp, the editor should optionally display a user‑visible error notification explaining that the link could not be parsed. This notification should only be shown when the caller explicitly requests error feedback. The parsing logic must be tolerant: it should accept incomplete timestamps (e.g., "10:44" meaning ten minutes and forty‑four seconds) and reject clearly malformed inputs (such as missing separators or out‑of‑range values). The timestamp parsing component should expose a strict regular expression for use by other parts of the application, such as the chat message formatter, which creates clickable links that open the editor at the specified time.

The overall behavior must be observable from the user interface: typing a valid timestamp and pressing enter (or any commit action) results in the playback position updating instantly, and any referenced hit‑object becoming selected. Invalid input either leaves the editor unchanged or, when error notification is enabled, shows a brief warning. This functionality should be accessible through the public editor API so that other modules can programmatically request a timestamp jump with the same error‑handling semantics.
