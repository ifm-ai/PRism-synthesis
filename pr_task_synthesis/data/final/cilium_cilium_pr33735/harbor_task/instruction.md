When the clustermesh subsystem stops fetching the configuration of a remote cluster, a rare race condition can cause the whole process to hang. The shutdown sequence cancels a context, which unblocks a select statement and returns from the retrieval function. However, a background controller may still attempt to deliver the fetched configuration through an internal communication mechanism that expects a receiver. If the receiver has already exited, the send operation blocks indefinitely, leading to a deadlock that prevents the controller from terminating and can stall the entire clustermesh component.

The desired behavior is that stopping the configuration retrieval never results in a blocked send, even if the receiving side has already stopped listening. The retrieval logic should be able to complete its work and allow the controller to finish without waiting for a receiver that no longer exists. This ensures that context cancellation and controller shutdown proceed smoothly, and the system remains responsive. The fix must guarantee that the communication path used to pass the configuration cannot cause the caller to block when the receiver is gone, thereby eliminating the deadlock scenario observed in CI and reproducible tests.
