When the bpfman RPC server is started as a long‑running process it currently aborts because the directory that should contain the Unix domain socket (by default /run/bpfman-sock) does not exist. In addition, no log output is produced from the RPC binary, making troubleshooting difficult. The required behavior is twofold. First, the RPC binary must ensure that the socket directory exists before attempting to bind the socket, creating it automatically if it is missing. When the optional CSI support flag is enabled, a second sub‑directory for CSI sockets must also be created. If directory creation fails, the program should return a clear error indicating the inability to create the required path. Second, both the RPC binary and the main CLI binary need to perform logging initialization at startup. If the process is running under systemd (i.e., a journal is available), logs should be directed to the journal using the systemd journal logger; otherwise, they should fall back to a standard environment‑logger. The log level must be driven by the RUST_LOG environment variable, and invalid values should be reported without causing a panic. After these changes, invoking the RPC binary with default arguments should succeed, the socket directory should be present, and log messages should appear either in the journal or on standard output according to the execution context.
