The relay component must be extended to handle IPv6 addresses throughout the allocation and channel binding workflow. When a client sends an authenticated Allocate request that specifies an IPv6 address family, the server must reply with a successful Allocate response that includes the allocated IPv6 relay address and the requested lifetime. After allocation, the client will issue a ChannelBind request referencing a channel number; the server must accept this request and return a ChannelBind success response. Once the channel is bound, the client will send ChannelData messages addressed to that channel. The server must forward the payload to the IPv6 peer using the peer's socket address and the standard UDP port (49152 in the tests). Conversely, when the IPv6 peer sends a UDP packet to the relay, the server must encapsulate the payload in a ChannelData message and deliver it back to the original client on the bound channel. The implementation must correctly match the IP version of the peer address against the allocation’s supported address families, rejecting bindings only when there is a version mismatch. Additionally, the relay must expose a public check (e.g., a function) that determines whether a given allocation can relay to a supplied socket address, returning true for IPv6 addresses when the allocation includes an IPv6 relay address and false otherwise. All existing IPv4 allocation, binding, and data forwarding behavior must remain unchanged and continue to pass their tests.
