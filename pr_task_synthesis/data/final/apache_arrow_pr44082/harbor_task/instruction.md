The Parquet Arrow benchmark suite currently reports misleading performance numbers. In several cases the values shown for items processed per second and bytes processed per second are identical, even though they represent different quantities. Moreover, the byte rate for boolean columns is calculated as if each value occupies a full byte, ignoring the fact that booleans are bit‑packed. This leads to inflated byte‑per‑second figures and makes it impossible to compare write and read speeds across data types accurately. The required change is to adjust the benchmark’s metric collection so that the number of items processed is counted separately from the number of bytes actually transferred. The byte count must be derived from the true storage size of each column type: for fixed‑width numeric types it should be the item count multiplied by the size of the underlying C type, for 16‑bit floating‑point values it should use two bytes per item, and for boolean columns it should use the bit‑packing utility to compute the exact number of bytes needed to store the given number of bits. After computing these values, the benchmark framework should be instructed to record the item count and byte count independently, allowing the output to display distinct "items_per_second" and "bytes_per_second" columns that reflect the real workload.

When the corrected implementation is in place, running the parquet‑arrow‑reader‑writer‑benchmark should produce output where the "bytes_per_second" column varies appropriately with the data type and matches the expected storage size, while the "items_per_second" column consistently reflects the total number of values processed. Boolean benchmarks should now show a much lower byte rate than before, and all other types should retain accurate byte rates. The benchmark should continue to function for all supported column types (e.g., 32‑bit integers, 64‑bit integers, double‑precision floats, and booleans) without altering the core functionality of reading or writing Parquet files.
